1. Битрикс за 30 секунд

1С-Битрикс — это CMS: каркас, который принимает запрос, находит страницу, собирает её из готовых блоков и отдаёт HTML. Внутри всё делится на слои. Сверху вниз: чем ближе к пользователю, тем «настраиваемее»; чем ниже, тем «системнее».

Страница PHP-файл в корне сайта: index.php, services/detail.php. Решает, что показать, и вызывает компоненты.
Шаблон сайта Общая обёртка: header.php, footer.php, стили, скрипты, меню. Здесь лежат шаблоны компонентов проекта.
Компонент Готовый блок с логикой: список новостей, детальная страница, форма, меню, крошки. Получает параметры и рисует HTML через свой шаблон.
Модуль Крупная подсистема ядра: iblock (инфоблоки), main, search, sale, form. Модуль даёт API, таблицы БД, настройки и часто — свои компоненты.
Ядро Каталог /bitrix/: загрузчик, классы, кэш, админка. Обновляется вендором и в git проекта не входит.
Данные Инфоблоки и их элементы в MySQL; настройки — в b_option, пользователи — в b_user, письма — в b_event.
Главная мысль. Модуль даёт возможности, компонент — вывод, инфоблок — данные, шаблон — внешний вид, страница — сценарий. Это разные вещи, и путать их — самая частая ошибка новичка.

2. Модуль module

Модуль — это подсистема ядра Битрикса, которая устанавливается, обновляется и отключается целиком. У модуля есть код, свои таблицы в БД, настройки, права и часто свои компоненты и почтовые события.

Где лежит

/bitrix/modules/<код модуля>/ install/ — установка: создание таблиц, настроек, демо-данных include.php — подключается при загрузке модуля classes/ — классы API (например, CIBlockElement) options.php — страница настроек в админке admin/ — файлы админ-страниц модуля lang/ — переводы

Код модуля не принято править: при обновлении ядра изменения в /bitrix/ затираются. Своя логика живёт в /local/ и подключается через события.

Модуль ≠ компонент. iblock — модуль. bitrix:news.list — компонент, который пользуется модулем iblock. Отключили модуль — компонент перестал работать, хотя файлы компонента на месте.

3. Компонент component

Компонент — переиспользуемый блок страницы: получает параметры, достаёт данные через API модулей и рисует HTML своим шаблоном. Вызов выглядит так:

<?php
$APPLICATION->IncludeComponent(
    'bitrix:news.list',          // пространство имён и имя компонента
    'nlb_cards',                 // шаблон компонента
    [                            // параметры
        'IBLOCK_TYPE' => 'nlb_content',
        'IBLOCK_ID'   => nlb_iblock_id('news'),
        'NEWS_COUNT'  => 6,
        'CACHE_TIME'  => 3600,
    ],
    false,
    ['HIDE_ICONS' => 'Y']
);
?>

Из чего состоит компонент

Логика

component.php или класс компонента: проверяет параметры, выбирает данные, складывает их в $arResult.

Шаблон

template.php: только вывод. Получает $arResult и $arParams, не должен ходить в БД.

Модификатор

result_modifier.php: подготовка данных до шаблона (сортировка, денормализация, добавление полей).

Эпилог

component_epilog.php: выполняется после шаблона, в том числе при отдаче из кэша (счётчики, метки).

Где ищется шаблон

Битрикс смотрит сверху вниз и берёт первое совпадение:

  1. /local/templates/<шаблон сайта>/components/<vendor>/<имя>/<шаблон>/
  2. /bitrix/templates/<шаблон сайта>/components/<vendor>/<имя>/<шаблон>/
  3. /local/components/<vendor>/<имя>/templates/<шаблон>/
  4. /bitrix/components/<vendor>/<имя>/templates/<шаблон>/
Поэтому шаблоны проекта лежат в www/local/templates/nlb_bootstrap/components/bitrix/... и переопределяют штатные шаблоны из /bitrix/. Ядро при обновлении их не трогает.

Кэш компонента

Компонент сам решает, кэшировать ли результат: CACHE_TIME в параметрах, startResultCache() / endResultCache() в коде. Кэш лежит в /bitrix/managed_cache/.

Правило стенда: поменяли шаблон, данные инфоблока или меню — сбросьте кэш. Иначе браузер и сервер покажут старое, и будет казаться, что правка «не применилась».

4. Инфоблок infoblock

Инфоблок — это хранилище однотипного контента: новости, услуги, товары, заявки. Не «таблица в админке», а сущность модуля iblock со своей структурой, правами, настройками и API.

Тип инфоблокаГруппа инфоблоков с общими настройками. На стенде три: nlb_content, nlb_catalog, nlb_services.
ИнфоблокКонкретное хранилище: «Новости», «Услуги», «Заявки на услуги». У него есть код (news, services), ID и свойства.
РазделИерархия внутри инфоблока (например, категории новостей). Может отсутствовать — у заявок разделов нет.
ЭлементОдна запись: новость, услуга, товар, бронь. У элемента есть поля и значения свойств.
СвойствоДополнительное поле, своё у каждого инфоблока: цена, телефон, дата, статус, картинка.

Поля элемента и свойства — не одно и то же

Поля (есть у всех)

  • ID — номер
  • NAME — название
  • CODE — символьный код для URL
  • XML_ID — внешний идентификатор
  • ACTIVE — Y/N (виден или нет)
  • SORT — порядок
  • PREVIEW_TEXT, DETAIL_TEXT — анонс и полный текст
  • DATE_ACTIVE_FROM, DATE_ACTIVE_TO — период показа

Свойства (свои у каждого инфоблока)

  • S — строка
  • N — число
  • L — список (enum): статус, цвет
  • F — файл: картинка, документ
  • E — привязка к элементу другого инфоблока
  • G — привязка к разделу
  • пользовательские типы: дата/время (DateTime), HTML/текст

Пример из брони: NAME — поле (название заявки), а SERVICE, DATE, TIME, STATUS — свойства инфоблока bookings.

ACTIVE, модерация и «почему заявки не видны»

ACTIVE = N — элемент существует в БД, но не выводится на сайте. Это не удаление. На стенде формы создают заявки с ACTIVE = N (режим модерации): сотрудник открывает элемент в админке, проверяет и включает. Политика модерации пока не зафиксирована — открытый пункт бэклога P0-8.

CODE, XML_ID и URL

  • CODE — человекочитаемый код для адреса: /services/observation-deck/.
  • XML_ID — стабильный идентификатор для миграций и повторного импорта: по нему элемент находят и обновляют, а не создают заново.
  • У заявок оба поля генерируются автоматически в обработчике OnBeforeIBlockElementAdd, чтобы не требовать их от посетителя.

Права

Доступ к инфоблоку задаётся группам пользователей: D — нет, R — чтение, W — запись, X — полный. В формах стенда стоит GROUPS => [2]: группа 2 — «Все пользователи», поэтому гость может отправить заявку, но не читать чужие.

API вместо SQL

Данные инфоблока читают и пишут через API, а не прямыми запросами:

CIBlockElement::GetList(
    ['SORT' => 'ASC'],
    ['IBLOCK_ID' => nlb_iblock_id('services'), 'ACTIVE' => 'Y'],
    false,
    false,
    ['ID', 'NAME', 'CODE', 'PREVIEW_TEXT']
);

Прямой SELECT по b_iblock_element обходит кэш, права, события и пользовательские типы свойств — так делать не нужно.

5. Шаблон сайта и страница template

Шаблон сайта — общая обёртка всех страниц: шапка, подвал, стили, скрипты, меню, счётчики. На стенде это nlb_bootstrap в www/local/templates/nlb_bootstrap/.

local/templates/nlb_bootstrap/ header.php — шапка: <head>, меню, хлебные крошки footer.php — подвал: контакты, скрипты, модалки styles.css — стили проекта script.js — поведение: меню, формы, слоты, push template_styles — описание шаблона для админки assets/ — bootstrap, иконки, картинки, push.js, pwa.js components/bitrix/ — переопределённые шаблоны компонентов

Страница — PHP-файл, который подключает пролог, шапку, компоненты и эпилог:

<?php
require $_SERVER['DOCUMENT_ROOT'] . '/bitrix/header.php';

$APPLICATION->SetTitle('Услуги');

$APPLICATION->IncludeComponent('bitrix:news.list', 'nlb_cards', [
    'IBLOCK_TYPE' => 'nlb_services',
    'IBLOCK_ID'   => nlb_iblock_id('services'),
]);

require $_SERVER['DOCUMENT_ROOT'] . '/bitrix/footer.php';
?>

ФайлЗачем

.top.menu.php, .left.menu.phpПункты меню рядом с разделом.

Крошки и заголовок

Цепочку навигации строит страница: $APPLICATION->AddChainItem('Услуги', '/services/'), а выводит компонент bitrix:breadcrumb. Заголовок — $APPLICATION->SetTitle(...), выводит шаблон сайта.

6. Как всё работает вместе

Путь одного запроса GET /services/observation-deck/:

  1. Apache + .htaccess — определяют, что это не файл, и отдают запрос urlrewrite.php.
  2. Пролог (/bitrix/modules/main/include/prolog.php) — подключает ядро, настройки, сайт, авторизацию.
  3. Шаблон сайта — header.php печатает <head>, меню, начало контента.
  4. Страница — services/detail.php находит услугу по коду и вызывает компоненты.
  5. Компонент — bitrix:news.detail через модуль iblock выбирает элемент (из кэша или из MySQL) и отдаёт $arResult в шаблон nlb_service.
  6. Шаблон компонента — рисует карточку услуги, тарифы и форму брони; форма снова вызывает компонент iblock.element.add.form.
  7. Эпилог — footer.php добавляет скрипты, модалки, закрывает документ.
Проверка понимания. Если на странице «нет услуги», проблема может быть на любом уровне: инфоблок пуст, элемент ACTIVE=N, не тот CODE, компоненту передан неверный IBLOCK_ID, шаблон не тот, или просто кэш. Поэтому диагностика идёт сверху вниз, а не «переписать шаблон».

7. События, агенты, кэш, почта

События (events)

Точки расширения ядра: можно подписаться на действие и выполнить свой код, не меняя /bitrix/.

AddEventHandler('iblock', 'OnBeforeIBlockElementAdd', 'nlb_forms_before_add');
AddEventHandler('iblock', 'OnAfterIBlockElementAdd',  'nlb_forms_after_add');
AddEventHandler('iblock', 'OnAfterIBlockElementUpdate', 'nlb_forms_after_update');

Так на стенде работают проверка занятого слота, авто-CODE/XML_ID, письма и дата обработки заявки.

Агенты (agents)

Отложенные задачи: «выполнить раз в N секунд». Живут в таблице b_agent. Запускаются либо на хитах посетителей, либо отдельным cron-процессом. На стенде cron — отдельный сервис cron; признак работы — b_agent.LAST_EXEC и www/db/logs/cron.log.

Кэш

  • Компонентный — CACHE_TIME, каталог /bitrix/managed_cache/.
  • Инфоблоков — теги и автогенерация при изменении элемента.
  • Меню и шаблонов — свой кэш у компонентов.
  • Сброс — в админке «Настройки → Автокэширование» или очистка каталога.

Почта

Код вызывает CEvent::Send('NLB_NEW_BOOKING', 's1', $fields). Письмо попадает в очередь b_event и отправляется по расписанию. Шаблон письма — «почтовое событие» в админке. Если SMTP не настроен, письмо остаётся в очереди с SUCCESS_EXEC = F — именно это происходит на стенде (блокер P0-1).

Пользователи, группы, права

Пользователь входит в группы; группы имеют права на модули и инфоблоки. Администратор — группа 1, «Все пользователи» — группа 2. Права на инфоблок задаются отдельно от прав на админку.

Как контент попадает в инфоблоки

Стенд воспроизводимый: структура описана кодом, а не собрана руками в админке.

  • www/db/config/iblocks.php — типы, инфоблоки, свойства, права.
  • www/db/config/data/*.php — элементы: новости, услуги, товары, события.
  • www/db/migrations/001…013 — пошаговое применение: типы → инфоблоки → свойства → разделы → элементы → меню → шаблон → заявки → сувениры → почта.
  • db/run.php — запуск миграций, db/check.php — сверка, db/lint.php — синтаксис, db/tests/run.php — проверки.
Почему так. Инфоблок, созданный руками, нельзя повторить на новом стенде и сложно откатить. Миграция описывает структуру и данные кодом: стенд поднимается с нуля одной командой, а расхождения ловит db/check.php.

10. Частые путаницы

«Модуль» и «компонент»

iblock — модуль. bitrix:news.list — компонент. Модуль не выводит HTML на страницу, компонент не создаёт таблиц в БД.

«Инфоблок» и «компонент»

Инфоблок хранит данные, компонент их показывает. Один инфоблок могут выводить десять разных компонентов и шаблонов.

Два вида шаблонов

Шаблон сайта — обёртка страниц. Шаблон компонента — разметка одного блока. Это разные каталоги и разные задачи.

ACTIVE = N — не удалено

Элемент лежит в БД, но скрыт. Удаление — отдельная операция. Заявки на стенде создаются неактивными и ждут модерации.

Свойство — не поле

NAME, CODE, ACTIVE есть у всех элементов. Цена, телефон, дата, статус — свойства конкретного инфоблока.

news.list — не только новости

Это универсальный вывод списка элементов любого инфоблока: услуг, товаров, событий. Название историческое.

Правки в /bitrix/

Затрутся при обновлении ядра. Своё — в /local/: шаблоны, обработчики, компоненты, модули.

«Ничего не изменилось»

Почти всегда кэш: компонентный, инфоблока или браузера. Сначала сброс кэша, потом поиск ошибки в коде.

Группа 2 — не админ

Группа 1 — администраторы, группа 2 — все пользователи. GROUPS => [2] в форме разрешает отправку гостю.

Почтовое событие — не письмо

Событие — шаблон с подстановками (#NAME#). Письмо — запись в b_event. Одно событие может отправить тысячи писем.

12. Словарь

ТерминЗначение
ЯдроКаталог /bitrix/: классы, загрузчик, админка, кэш. Обновляется вендором.
МодульПодсистема ядра с API, таблицами и настройками: iblock, main, search.
КомпонентБлок страницы с логикой и шаблоном: bitrix:news.list.
Шаблон компонентаРазметка вывода компонента: nlb_cards, nlb_service.
Шаблон сайтаОбщая обёртка страниц: header.php, footer.php, стили.
ИнфоблокХранилище однотипного контента со свойствами и правами.
Тип инфоблокаГруппа инфоблоков с общими настройками: nlb_content, nlb_catalog, nlb_services.
ЭлементОдна запись инфоблока: новость, услуга, товар, бронь.
РазделКатегория внутри инфоблока; у заявок разделов нет.
СвойствоДополнительное поле инфоблока: цена, телефон, дата, статус.
Список (enum)Свойство типа L с фиксированными значениями: статус new/confirmed/cancelled.
ACTIVEПризнак показа элемента: Y — виден, N — скрыт (модерация).
CODEСимвольный код для URL и поиска элемента.
XML_IDВнешний идентификатор для миграций и повторного импорта.
Пролог / эпилогСлужебные части страницы: инициализация ядра и завершение вывода.
СобытиеТочка расширения: OnBeforeIBlockElementAdd и подобные.
АгентОтложенная задача в b_agent, выполняется по расписанию или на хитах.
Почтовое событиеШаблон письма с подстановками; отправка — через CEvent::Send.
Очередь писемТаблица b_event; без SMTP письма копятся с SUCCESS_EXEC = F.
КэшСохранённый результат компонента или выборки; сбрасывается вручную или по тегам.
HL-блокHighload-блок: лёгкая таблица для справочников, кандидат для расписания услуг.
МиграцияPHP-скрипт стенда, который создаёт структуру и данные инфоблоков кодом.
